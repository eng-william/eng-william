<a id="modelagem-relacional"></a>
## 🧱 1. Modelagem Relacional: A Base Clássica

A **modelagem relacional** (Edgar F. Codd, 1970) organiza os dados em **tabelas** com linhas (registros) e colunas (atributos). É o modelo tradicional usado em bancos SQL.
Ela é pensada para **manter consistência**, reduzir erros e garantir que cada informação tenha um lugar certo. Por isso, é muito comum em sistemas que precisam registrar transações com precisão, como bancos, ERPs e e-commerces.
Quando bem desenhada, facilita tanto a manutenção quanto a evolução do sistema ao longo do tempo.

### 🗝️ Chaves (Keys)

* **Chave Primária (PK):** identifica um registro de forma única.
* **Chave Estrangeira (FK):** aponta para a PK de outra tabela (relacionamento).
* **Chave Natural:** já existe no mundo real (ex.: CPF, CNPJ).

### 🧼 Normalização

Normalização evita redundância e inconsistência.

* **1NF:** sem grupos repetidos, valores únicos por coluna, PK definida.
* **2NF:** tudo depende **inteiramente** da PK.
* **3NF:** nada depende de outro atributo não-chave (sem dependência transitiva).

> 🎯 **Meta comum:** chegar na **3NF** para manter dados confiáveis e limpos.

### 🕒 Histórico de Mudanças

Para guardar histórico:
* Cria-se uma **tabela de histórico**
* Copia-se o registro original
* Adiciona-se **timestamp** e **usuário**

### ✅ Quando usar

* Sistemas transacionais (OLTP)
* Integridade e consistência são prioridade
* Dados muito atualizados

## ⭐ 2. Modelagem Dimensional: Fatos e Dimensões

A **modelagem dimensional** surgiu para **análise e BI**, organizada em **fatos** e **dimensões**.
Ela simplifica o entendimento do negócio, deixando as perguntas analíticas mais fáceis de responder. Em vez de muitas tabelas interligadas, o foco é em um modelo mais direto, pensado para leitura e agregações rápidas.
É o padrão mais usado em **Data Warehouses** e dashboards de performance.

### 📊 Fatos

* Métricas numéricas (ex.: vendas, receita, quantidade)
* São agregáveis (soma, média, contagem)

### 🧭 Dimensões

* Descrevem o contexto (tempo, produto, cliente, região)
* Usam hierarquias (ex.: Ano → Mês → Dia)

### 🧩 Chaves Substitutas (Surrogate Keys)

* Chaves artificiais geradas pelo sistema
* Evitam problemas quando chaves naturais mudam

### 🕰️ SCDs (Slowly Changing Dimensions)

* **Tipo 1:** sobrescreve (sem histórico)
* **Tipo 2:** cria nova linha (histórico completo)
* **Tipo 3:** adiciona coluna (histórico limitado)

### ✨ Esquema em Estrela (Star Schema)

```
           Dim Tempo
              |
Dim Produto — Fato Vendas — Dim Cliente
              |
           Dim Loja
```

### ✅ Quando usar

* Data Warehouse e BI
* Dashboards e relatórios
* Performance em leitura é crítica

## 🧭 3. CDM e Data Vault: Padronização e Rastreio

Essas abordagens aparecem quando a empresa precisa **integrar muitos sistemas** e manter um histórico confiável ao longo do tempo. A ideia é criar um padrão de linguagem e de estrutura para que dados de origens diferentes conversem entre si.
São muito úteis em ambientes corporativos grandes, onde mudanças de fonte acontecem com frequência.

### 🧩 CDM (Common Data Model)

* Linguagem de dados **padronizada**
* Facilita integração entre sistemas e fornecedores
* Útil em ecossistemas grandes e complexos

### 🏛️ Data Vault (Daniel Linstedt, 2000)

Foca em **escala** e **histórico** usando três entidades:

* **Hubs:** entidades centrais (Cliente, Produto)
* **Links:** relacionamentos (Cliente-Compra)
* **Satélites:** atributos descritivos (nome, endereço, status)

✅ **Vantagens**
* Histórico detalhado
* Evolução fácil
* Resiliência a mudanças

⚠️ **Desvantagens**
* Muitas tabelas
* Complexidade maior
* Performance pode sofrer sem boas práticas

<a id="abordagem-inmon"></a>
## 🏢 4. Abordagem Inmon (Top-Down)

A visão de **Bill Inmon** parte de uma base corporativa única, bem integrada e altamente normalizada. A ideia é criar primeiro um núcleo de dados consistente e detalhado, e depois distribuir esse conteúdo para áreas específicas por meio de Data Marts.
É uma abordagem que prioriza **governança**, **padronização** e **integração corporativa** desde o início.

### 🧠 Conceito central: CIF

* **Corporate Information Factory (CIF)** como núcleo do DW
* Base corporativa em **3NF** com dados atômicos
* Data Marts **dependentes** alimentados a partir do centro

### ✅ Pontos fortes

* Visão corporativa única
* Alta consistência e qualidade dos dados
* Melhor controle de regras e padrões

### ⚠️ Desafios

* Tempo maior para gerar valor
* Requer mais esforço inicial de integração
* Pode ser percebida como “lenta” para o negócio

---

<a id="abordagem-kimball"></a>
## 🧱 5. Abordagem Kimball (Bottom-Up)

Na visão de **Ralph Kimball**, o foco é entregar valor rápido ao negócio com **Data Marts dimensionais**. As áreas começam a trabalhar com os dados o quanto antes, e a integração acontece por meio de **dimensões conformadas**.
É uma abordagem prática, muito usada quando o negócio precisa de **agilidade** e resultados rápidos.

### 🧠 Conceito central: DW Bus

* Data Marts dimensionais como base
* Integração via **DW Bus Matrix**
* Dimensões conformadas para manter consistência

### ✅ Pontos fortes

* Entrega rápida de valor
* Fácil entendimento para o usuário de negócio
* Modelo otimizado para análise

### ⚠️ Desafios

* Risco de silos se não houver governança
* Integração pode ficar complexa com o tempo
* Exige disciplina no uso das dimensões conformadas

<a id="visao-hibrida"></a>
## 🔀 6. Visão Híbrida: Integrando as Duas Escolas

Na prática, muitas empresas **combinam** as duas abordagens. O modelo híbrido usa uma base integrada (Inmon) para garantir consistência e um conjunto de Data Marts dimensionais (Kimball) para acelerar o consumo.
É o equilíbrio entre **governança** e **agilidade**, unindo o melhor dos dois mundos.

### ✅ Como funciona na prática

* **3NF para integração** e qualidade dos dados
* **Dimensional para consumo** e performance analítica
* Camadas bem definidas entre integração e entrega

> ✅ Mito: Kimball não ignora visão corporativa  
> ✅ Mito: Inmon não exige "Big Bang" (ele defende evolução iterativa)

<a id="views-oltp"></a>
## 🪞 7. Views e OLTP Espelhado: Facilitando o ETL

Essas técnicas são mais “operacionais” e ajudam no dia a dia do time de dados. O foco é **simplificar a extração** e **reduzir impacto** nos sistemas críticos, sem perder qualidade no resultado.
Elas costumam ser aplicadas quando o ETL é pesado e o sistema de produção não pode sofrer lentidão.

### 👓 Views

* Tabelas virtuais via SQL
* Renomeiam campos e simplificam o ETL
* Podem simular um esquema estrela mesmo em bases complexas

**Exemplo simples:**
```sql
CREATE VIEW vw_vendas AS
SELECT
  p.id_pedido,
  c.nome_cliente,
  p.valor_total,
  p.data_pedido
FROM pedidos p
JOIN clientes c ON c.id_cliente = p.id_cliente;
```

### 🪞 OLTP Espelhado (Mirrored OLTP)

* Copia o banco transacional
* ETL roda no espelho, não no sistema principal
* Permite criar índices específicos sem impactar produção

### ✅ Quando usar

* ETL pesado
* Sistemas críticos que não podem “parar”
* Necessidade de performance na extração

## 📚 8. Analogia: A Biblioteca de Dados

Analogias ajudam a fixar o conceito de forma simples. Aqui a ideia é comparar cada abordagem com uma parte da biblioteca para mostrar como cada modelo organiza e serve os dados de um jeito diferente.
Essa visão facilita o entendimento para quem está começando e quer enxergar o todo.

Imagine que seus dados são uma **biblioteca**:

* **Relacional:** livros catalogados em prateleiras exatas, tudo organizado e sem repetição.
* **Dimensional:** uma estante temática com resumos prontos para pesquisa rápida.
* **CDM:** padrão de catalogação único para todas as bibliotecas da cidade.
* **Data Vault:** histórico completo de cada livro e empréstimo, mesmo que mude de nome.
* **Inmon:** primeiro constrói a biblioteca central, depois cria salas por assunto.
* **Kimball:** monta salas por assunto e depois conecta tudo com um catálogo comum.
* **Views:** etiquetas novas para facilitar a busca.
* **OLTP Espelhado:** cópia da biblioteca para pesquisa, sem atrapalhar quem está lendo.

> 💡 **Conclusão:** não existe um modelo perfeito. O segredo é escolher o mais adequado ao objetivo do negócio e ao tipo de uso dos dados.
